# LlaMask 模型评测与首发冻结结论

文档状态：V1.0，首轮模型组合已冻结

评测日期：2026-07-31

## 1. 最终选择

首发不使用单一模型。默认检测链路冻结为：

1. 确定性格式、校验位、上下文规则。
2. `SiameseUIE Chinese base`：高速抽取姓名、机构和客户实体。
3. `Qwen3.5-4B Q4_K_M`：补充复杂语义实体并处理冲突。
4. `PP-OCRv6 small`：普通图片、扫描页和内嵌图片的快速 OCR。
5. `PP-OCRv6 medium`：高安全模式和困难页面的 OCR。

`PP-DocLayoutV3` 暂不进入首发默认包。原生 Office 文件使用自身结构，
PDF/图片先使用 OCR 多边形；只有真实复杂版面语料证明阅读顺序或区域切分
是主要漏检来源时，再加入版面模型。

`PP-UIE-0.5B` 暂缓。SiameseUIE 已用更小权重和约 13 ms/片段的 ONNX CPU
延迟，把冻结测试集的最终召回从 95% 左右提高到 99% 以上。继续增加
一个 0.5B 生成式抽取模型的增益上限很小，却会增加一套 Paddle 运行时和
跨平台维护成本。

## 2. 评测环境与数据

- 主机：Apple M5 Max、18 核、128 GB 内存、macOS arm64。
- LLM 运行时：固定到
  `llama.cpp@47f686f53f2a20fe82d87d79fa5c835714ee8f46`，Metal 开启，
  网络功能关闭。
- 当前主机不代表 16 GB 最低目标机，延迟只能用于方案之间的相对比较。
- 文本集：1,800 条确定性生成的中文/中英混合片段，13 类敏感实体；
  360 条开发集、1,440 条测试集。模型冻结使用独立的 360 条测试子集。
- OCR 基础集：240 张合成页面。
- OCR 压力集：320 张，包含透视、阴影、低清、强压缩、表格线和印章遮挡。

文本集 SHA-256：
`13f30c6ff48ec1b255c88e5610b08b813acdec0cf796c9b86ef128a1b40d81b7`。

这些是受控合成数据，适合比较方案和防止回归，不能代替经授权的真实
DOCX、XLSX、PPTX、PDF、扫描件和拍照文件验收集。

## 3. 文本检测结果

### 3.1 组合对比

下表为精确 span 的 micro 指标。

| 方案 | 开发集 Precision | 开发集 Recall | 测试集 Precision | 测试集 Recall | 测试集 F1 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 基础格式规则 | 95.39% | 17.90% | — | — | — |
| 上下文规则 | 100.00% | 44.58% | — | — | — |
| Qwen Q4 单独 | 96.25% | 83.24% | 95.45% | 81.53% | 87.94% |
| 规则 + Qwen Q4 | 99.42% | 96.06% | 98.70% | 94.86% | 96.74% |
| 规则 + SiameseUIE | 98.54% | 95.07% | 98.86% | 95.97% | 97.39% |
| 规则 + Qwen Q4 + SiameseUIE | **99.58%** | **99.44%** | **99.44%** | **99.17%** | **99.30%** |

冻结测试子集共有 720 个实体。最终组合命中 714 个，误报 4 个，漏报
6 个；受约束 JSON 和 span 对齐有效率为 100%。

关键结论：

- 规则负责号码、地址、金额、工资、业务指标、项目代码和合同号，速度低于
  0.01 ms/片段。
- Qwen 和 SiameseUIE 单独都达不到自动导出的安全目标，但两者的语义漏检
  不重合，组合收益明显。
- 最终组合中，地址、电话、邮箱、身份证、银行卡、财务金额、工资、
  业务指标、项目代码和合同号在本测试子集均为 100% 召回。
- 剩余错误集中在少量人名和机构边界；产品仍必须保留人工修改、低置信拦截
  和导出后二次残留检查。

### 3.2 Qwen BF16 与 Q4_K_M

官方 BF16 权重由固定版本 `llama.cpp` 自行转换，随后量化为 Q4_K_M，
没有使用第三方社区 GGUF。

| 指标 | BF16 | Q4_K_M |
| --- | ---: | ---: |
| GGUF 文件 | 8,424,393,056 B | 2,708,803,936 B |
| 峰值 RSS | 8.38 GiB | 3.17 GiB |
| 同一 60 条的单模型 Recall | 91.15% | 83.19% |
| 同一 60 条的完整组合 Recall | 99.12% | 99.12% |
| 同一 60 条平均 LLM 耗时 | 1,880 ms | 1,298 ms |
| 结构化输出有效率 | 100% | 100% |

Q4 单模型有可见精度损失，但规则和 SiameseUIE 恰好补回了这批差异，
完整组合结果与 BF16 相同。Q4 将模型文件减少约 68%，峰值内存减少约
62%，因此冻结为普通用户默认版本。BF16 只保留为评测基线，不进入默认包。

Q4 文件 SHA-256：
`cd083c9ab9093c887bbf1f5b5f010b6899596555d4e5cf507a6bdc263030f534`。

开发进度更新（2026-07-31）：Qwen Q4 已通过标准输入 sidecar 接入，不把
原文放入进程参数，也不启动本地 HTTP 服务。该路径每次处理一个片段，而
冻结评测使用 6 条批量输入；前 6 条对照中，单记录 sidecar 为 P 75%、
R 60%，原批量路径为 P 100%、R 70%。因此当前 Qwen sidecar 只提供未校准
的人工复核建议，不能直接继承本节冻结指标。

## 4. OCR 对比

| 数据集 | 模型 | 字符准确率 | 敏感片段完整召回 | 敏感区域覆盖 | 平均每页 |
| --- | --- | ---: | ---: | ---: | ---: |
| 基础 240 页 | small | 99.04% | 100.00% | 100.00% | 117 ms |
| 基础 240 页 | medium | 98.99% | 99.78% | 100.00% | 541 ms |
| 压力 320 页 | small | 90.18% | 85.05% | 97.11% | 116 ms |
| 压力 320 页 | medium | 93.88% | 89.07% | 99.36% | 655 ms |

medium 在困难页上提高约 4 个百分点的敏感片段召回，但约慢 5.7 倍。
因此：

- small 用于拖入文件后的快速预览和普通批量任务。
- medium 用于用户选择的“高安全模式”、低质量页面和导出前复扫。
- 印章压字和“低清 + 透视 + 阴影”的复合失真仍可能失败；这类页面应
  标为需复核，或使用扩大区域/整行打码的保守策略。
- 不能让视觉大模型替代 OCR 坐标；VLM 可解释页面语义，但不能作为唯一
  的精确打码定位器。

模型文件：

| OCR 档位 | 检测 + 识别权重 |
| --- | ---: |
| small | 31,039,890 B |
| medium | 138,587,816 B |

开发接入更新（2026-07-31）：PP-OCRv6 small 已通过只读 Python sidecar
接入 Rust 图片管线。运行注册表固定检测/识别 ONNX、配置、sidecar 和解释器
的 SHA-256；请求同时携带源图片 SHA-256，核心会复核响应宽高与全部坐标。
PNG、JPEG 已完成真实“扫描 → 片段矩形 → 实心打码 → 再次 OCR”回归，
包括一个被 OCR 拆成两行的银行卡号。规则模式下，当前一次一进程的完整 CLI
扫描约 3～4 秒，其中大部分是 Paddle/Python 模型启动；上表 117 ms 是模型
已加载后的单页推理时间。后续持久工作进程主要优化启动延迟，不改变冻结
模型选择。

图片轻量 AI 配置把 OCR 与 SiameseUIE 放入同一运行注册表。当前双行样图
的 OCR + 一次 SiameseUIE 扫描约 12 秒；SiameseUIE 的 0.85 未校准结果在
默认 0.90 自动阈值下进入人工确认。Qwen 暂不放入图片默认运行配置，避免
其单记录语义漂移和每页重复加载 4B 权重；它需要在持久批处理 sidecar 完成
后再接入。

## 5. SiameseUIE 的收益与代价

- 原 PyTorch 权重：409,159,785 B。
- FP32 ONNX 单文件：407,056,303 B，SHA-256
  `7606ed777399ebaba2227ff009777758003be88674282e5c40b36ec40bcf2097`。
- 1,440 条测试记录的 ONNX CPU 平均延迟：12.7 ms/片段；旧 PyTorch
  路径为 24.5 ms/片段。
- ONNX 峰值 RSS：0.73 GiB；旧 PyTorch 路径为 1.04 GiB。
- 规则 + Qwen 的测试召回为 94.86%；加入 SiameseUIE 后为 99.17%。
- 它对 Qwen 漏掉的人名和机构形成有效互补，并能在客户名单上下文中
  提供稳定 span。

开发进度更新（2026-07-31）：SiameseUIE 已导出为正文只编码一次、权重
只存一份的动态 ONNX 单图。纯 ONNX sidecar 不再导入 PyTorch、
Transformers 或 ModelScope；最小依赖环境约 104 MiB，便携 Python 3.12
运行时约 72 MiB，连同模型约 564 MiB。旧 360 条冻结预测与 PyTorch
逐条零差异，真实 Rust 扫描和启动前 SHA-256 校验也已通过。

动态 INT8 实验文件为 322,761,115 B，只比 FP32 小约 20.7%，速度约快
6%；它在完整 1,440 条测试记录中改变了 26 条实体决策。虽然这批合成集
的总体召回略有上升，但阈值附近的语义漂移不可控，因此首发默认保留 FP32，
INT8 只作为后续校准候选。

原接口不提供校准概率，当前 sidecar 继续使用保守运行值 0.85，并在默认
0.90 自动处理阈值下要求人工确认。剩余发布门槛是 Windows x64、Apple
Silicon 目标机一致性和便携包签名，不再是模型格式导出。

## 6. 首发体积与硬件判断

默认模型权重约为：

- Qwen Q4：2.71 GB。
- SiameseUIE：0.41 GB。
- OCR small + medium：0.17 GB。
- 合计约 3.29 GB（十进制）。

运行库、桌面应用、tokenizer、字体、文档转换组件和许可证还会增加体积。
SiameseUIE 模块的开发实测总量约 564 MiB；建议把完整离线安装包目标暂定
为 4.5～6 GB，仍需以双平台实际打包结果为准。

硬件建议：

- 8 GB：规则 + SiameseUIE + small OCR 的轻量模式；Qwen 按需或不安装。
- 16 GB：默认完整模式，模型顺序加载；Q4 峰值约 3.17 GiB，具备可用空间。
- 24 GB 以上：仍使用 4B Q4；暂不增加 9B，除非真实语料证明有至少
  3 个百分点的组合召回收益。

## 7. 冻结后的开发门

可以开始文件管线和桌面产品开发，但不能把本轮合成指标直接写成产品宣传。
进入公开发布前还需要：

1. 在代表性的 16 GB Windows 和 macOS 设备复测速度、内存、能耗和断网行为。
2. 建立经授权、去标识化的真实文件集，覆盖全部目标格式和复杂版式。
3. 在双平台完成 SiameseUIE ONNX 便携打包、签名和算子一致性验证。
4. 验证 DOCX/XLSX/PPTX/PDF 的回写、残留数据、批注、修订、隐藏对象和
   导出后二次扫描。
5. 对允许跳过人工复核的策略单独计算文件级漏检率，不能只使用实体平均值。
6. 用真实复杂页面决定是否加入 PP-DocLayoutV3 或文档视觉增强模型。
