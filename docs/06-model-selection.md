# LlaMask 本地模型选型报告

文档状态：V0.2，资料调研完成；最终实测结论见
[模型评测与首发冻结结论](07-model-benchmark-results.md)

调研日期：2026-07-31

## 1. 结论

LlaMask 不适合用一个大语言模型包办全部检测。实测确认采用“确定性规则 +
OCR + 中文信息抽取 + 小型大模型复核”的组合。

首发冻结模型包含：

1. `Qwen3.5-4B` Q4_K_M：复杂语义复核。
2. `SiameseUIE Chinese base`：姓名、机构和客户名称的高速 span 抽取。
3. `PP-OCRv6 small`：快速预览和普通批量 OCR。
4. `PP-OCRv6 medium`：高安全模式和困难页 OCR。

PP-DocLayoutV3 和 PP-UIE-0.5B 暂缓，不进入默认包。运行时不同时加载全部
模型：规则和 UIE 先给出快速结果，Qwen 在后台补充，OCR 只对视觉内容加载。

冻结测试子集上，规则 + Qwen Q4 + SiameseUIE 的精确 span 召回为 99.17%、
精确率为 99.44%。这允许开始产品开发，但仍需真实授权文件和 16 GB 目标机
验证，不能把合成集指标直接作为发布承诺。

## 2. 模型与非模型的责任边界

| 工作 | 是否依赖模型 | 推荐实现 |
| --- | --- | --- |
| 手机号、邮箱、证件号、银行卡号 | 否，模型只处理歧义 | 正则、校验位、上下文规则 |
| 用户指定姓名、机构、项目代码 | 否 | 敏感词典、别名和规范化匹配 |
| 未预先列出的姓名、机构、地址 | 是 | 中文信息抽取模型产生候选，LLM 复核 |
| “这个数字是不是财务或业务秘密” | 是 | 规则先定位数字，LLM 根据局部上下文分类 |
| 图片文字和坐标 | 是 | OCR；不能让 LLM 猜测坐标 |
| 页面区域和阅读顺序 | 是 | 版面模型 |
| 文件解析、修改、打码和残留验证 | 否 | 确定性程序 |
| 一致替换与可逆映射 | 否 | 加密映射表 |
| 根据用户习惯学习 | MVP 不训练权重 | 本地词典、白名单、规则、反馈案例和策略版本 |

模型只能提出带来源和置信度的 `Finding`，不能直接修改文件。高风险号码不能因为 LLM 判定为“不敏感”而被放行。

## 3. 通用语义与视觉模型

### 3.1 推荐：Qwen3.5-4B

选择理由：

- 原生支持文字和图片，可同时承担文本歧义复核、局部页面截图理解和用户自然语言策略解释，避免再安装一套独立 VLM。
- 中文能力和指令遵循能力适合作为候选复核器。官方模型卡中，4B 的 C-Eval 为 85.1、IFEval 为 89.8；9B 分别为 88.2 和 91.5。公开分数只用于候选筛选，不能代替 LlaMask 自己的脱敏评测。
- Qwen 官方说明 Qwen3.5 支持 201 种语言，并提供 `llama.cpp` 和 Apple Silicon 的本地运行路径。
- Apache 2.0 许可证，适合商业桌面产品。

注意事项：

- 名称中的 4B 指语言模型规模；官方仓库将包含视觉部分的总规模显示为约 5B。
- 官方 BF16 仓库约 9.3GB。Q4 GGUF 的最终大小必须以我们自己转换并校验的文件为准，工程预估约 2.7～3.4GB。
- 模型默认会进入思考模式。LlaMask 应使用非思考模式、固定 JSON 语法约束、4K～8K 局部上下文和短输出。
- 模型发布较新，Windows CPU、Windows GPU 和 macOS Metal 上的量化精度、视觉输入和结构化输出稳定性都需要回归测试。

官方资料：

- [Qwen3.5 / Qwen3.6 官方仓库](https://github.com/QwenLM/Qwen3.6)
- [Qwen3.5-4B 官方模型卡](https://huggingface.co/Qwen/Qwen3.5-4B)
- [llama.cpp 官方仓库](https://github.com/ggml-org/llama.cpp)

### 3.2 可选增强：Qwen3.5-9B

优点：

- 官方通用与视觉基准普遍优于 4B，更适合复杂业务语义、隐晦表达和较长上下文。

缺点：

- BF16 仓库约 19.3GB，Q4 权重工程预估约 5.5～6.5GB。
- CPU 延迟和内存明显增加，不适合作为所有普通用户的强制下载。

取舍：

- 作为独立的“高准确度模型包”，不与 4B 同时加载。
- 只有当项目评估集上，9B 在上下文型敏感数据的召回率比 4B 提高至少 3 个百分点，才值得维护这个模型包。
- 推荐 24GB 及以上内存设备使用；最终硬件线由实测决定。

### 3.3 不选的方案

| 候选 | 不作为默认模型的原因 |
| --- | --- |
| Qwen3.5-0.8B / 2B | 体积小，但复杂中文业务语义和稳定 JSON 的风险更高；2B 可作为 8GB 轻量模式候选 |
| Qwen3-VL-4B | 专用视觉能力可用，但与 Qwen3.5-4B 功能重叠，会增加模型和运行时维护成本 |
| Qwen3.6-27B / 35B | 最新一代的小尺寸版本尚未出现；27B 以上不符合普通电脑离线使用目标 |
| 只使用 LLM | 逐段扫描速度慢、结果不够确定，也无法提供可靠的字符框和版面坐标 |

## 4. OCR 模型

### 4.1 推荐：PP-OCRv6 small + medium 双档

职责：

- 从图片、扫描 PDF 和 Office 内嵌图片中返回文字、置信度和坐标。
- 导出后重新 OCR，检查目标文字是否仍可识别。

优点：

- 一个模型系列覆盖中文、英文、日文和 46 种拉丁字母语言。
- 官方提供 tiny、small、medium 三档，medium 为 34.5M 参数。
- 官方报告 medium 相比 PP-OCRv5 server，检测准确率提升 4.6%、识别准确率提升 5.1%，并报告了 CPU 和 Apple M4 加速结果。
- Apache 2.0；提供多种本地推理路径，适合独立离线打包。

缺点：

- 2026 年 6 月发布，跨平台打包和新版本稳定性仍需验证。
- 场景文字、低分辨率截图、竖排文字、印章和手写体仍可能漏检。
- OCR 结果不能直接理解“这个数字的业务含义”，仍需规则或语义模型。

取舍：

- small 作为默认快速预览和普通批量配置。
- medium 作为高安全模式；困难集敏感片段召回比 small 高约 4 个百分点，
  但实测约慢 5.7 倍。
- OCR 的检测网络与识别网络在产品上视为一个模块，按页面批处理并在任务结束后卸载。

官方资料：

- [PaddleOCR 官方仓库与 PP-OCRv6 发布说明](https://github.com/PaddlePaddle/PaddleOCR)

### 4.2 不使用 VLM 替代常规 OCR

`PaddleOCR-VL-1.6` 是 0.9B 文档解析 VLM，官方在 OmniDocBench v1.6 报告 96.33%，对表格、公式、印章和图表很强。但首发不把它放进默认包：

- 它偏向把文档重建为 Markdown/结构化内容，而 LlaMask 更需要原文件中的精确坐标和可回写位置。
- 与 Qwen3.5 的视觉语义能力重叠。
- 增加约一个十亿参数模型及一套更复杂的推理依赖。

如果真实样本证明表格、公式或印章是主要漏检来源，再作为可选文档增强包评估。

官方资料：[PaddleOCR-VL-1.6 文档](https://www.paddleocr.ai/main/en/version3.x/algorithm/PaddleOCR-VL/PaddleOCR-VL-1.6.html)

## 5. 版面分析模型

### 5.1 暂缓：PP-DocLayoutV3

职责：

- 在扫描页和图片中识别标题、段落、表格、页眉页脚、图形等区域。
- 提供阅读顺序和区域坐标，帮助 OCR 分块、跨行实体合并和预览定位。

优点：

- 33.3M 参数，F32 权重约 132MB，体积小。
- 输出框或多边形、区域类别和阅读顺序。
- 针对旋转、弯曲、拍照、光照变化等文档场景设计。
- Apache 2.0。

缺点：

- 对纯文本页和简单截图没有必要。
- 模型较新，类别映射和坐标在不同运行时上的一致性需要验证。

取舍：

- 首发不随默认模型包安装；先使用文件自身结构和 OCR 多边形。
- 只有真实复杂版面语料证明阅读顺序或区域切分是主要漏检来源时再加入。
- 原生 DOCX/XLSX/PPTX 优先使用文件自身结构，不把 Office 页面截图后重新推断版面。

官方资料：[PP-DocLayoutV3 官方模型卡](https://huggingface.co/PaddlePaddle/PP-DocLayoutV3_safetensors)

## 6. 中文实体抽取模型

### 6.1 为什么还需要一个专用模型

姓名、机构、地址等实体会在长文档中大量出现。专用 span 模型能够快速给出原文起止位置，把 LLM 调用限制在真正有歧义的少量候选上。

但专用模型只有在项目数据上带来实际收益才应该进入安装包。最终实验需要同时比较“专用模型 + 4B 复核”和“直接由 4B 分块检测”。

### 6.2 第一候选：SiameseUIE Chinese base

优点：

- 面向中文的通用信息抽取，可由提示定义姓名、机构、业务项目、合同名称等类型。
- span/pointer 式抽取更容易映射回原文，不需要解析自由生成文本。
- 官方仓库约 409.5MB，Apache 2.0。
- 比 0.5B 生成式模型更轻，适合 CPU 扫描大量文本。

缺点：

- 公开结果不是隐私脱敏专项测试。
- 模型和工程生态相对旧，Windows/macOS 的 ONNX 导出与数值一致性尚未验证。
- 对用户临时定义的复杂业务概念，可能不如生成式模型。

官方资料：[SiameseUIE 中文 base 模型卡](https://modelscope.cn/models/iic/nlp_structbert_siamese-uie_chinese-base)

### 6.3 第二候选：PP-UIE-0.5B

优点：

- 官方明确支持中文和英文，可用自然语言 schema 定义抽取目标。
- 覆盖 NER、关系和事件抽取，后续可用少量标注样本微调。
- PaddleNLP 官方提供 0.5B、1.5B、7B 和 14B；只测试 0.5B。

缺点：

- 生成式推理比 encoder/span 模型慢，和 Qwen3.5 的能力重叠。
- 官方高性能路径更偏向 Paddle/CUDA 环境，macOS 和无独显 Windows 的打包成本较高。
- 额外增加约 0.5B 权重，只有准确度显著更高才值得使用。

官方资料：[PP-UIE 官方文档](https://paddlenlp.readthedocs.io/zh/latest/llm/application/information_extraction/README.html)

### 6.4 暂不选择：GLiNER2

GLiNER2 本身只有 205M 参数、CPU 友好、支持开放 schema，工程形态很有吸引力。但其现成 PII 多语言模型公开列出的语言为英语、法语、西班牙语、德语、意大利语、葡萄牙语和荷兰语，没有中文；模型卡也明确说明非欧洲文字没有测量。不能因“multilingual”标签就把它当作中文隐私模型。

只有出现官方中文权重，或我们自行微调并通过独立测试后，才重新进入候选。

官方资料：

- [GLiNER2 官方仓库](https://github.com/fastino-ai/GLiNER2)
- [GLiNER2 PII 多语言模型卡](https://huggingface.co/fastino/gliner2-privacy-filter-PII-multi)

### 6.5 最终进入默认包的条件

SiameseUIE 已通过首轮合成集门槛：加入后，冻结测试集组合召回从
94.86% 提升到 99.17%，平均 CPU 延迟约 24.5 ms/片段，峰值 RSS 约
1.04 GiB。它进入默认模型组合，但产品化仍以完成轻量 ONNX/原生导出为条件。

专用信息抽取模型需要同时满足：

- 姓名、机构和地址的组合召回率比“不使用专用模型”提高至少 3 个百分点，或将 LLM 复核次数降低至少 50%。
- 不能降低组合流水线的最终召回率。
- 峰值内存增量不超过 1GB。
- Windows x64 CPU 与 macOS Apple Silicon 均可离线运行。
- 能稳定返回精确原文 span；无法对齐原文的生成结果一律丢弃。
- 许可证、权重来源、哈希和转换过程可被固定。

若没有候选满足条件，首发不安装专用信息抽取模型，使用“规则 + 分块 Qwen3.5-4B”的简化方案。少一个模型比维护一个没有实证收益的模型更安全。

## 7. “学习能力”不需要第五个大模型

首发的学习能力应是可解释、可撤销的本地策略学习：

- 用户确认的敏感词、别名和上下文条件进入词典或规则。
- 用户取消的误报进入有作用域的白名单。
- 记住不同实体类型的默认脱敏动作。
- 记住文件夹或项目使用的策略。
- 保存少量经过用户确认的匿名化示例，供 LLM 复核时检索。

首发不训练或微调权重，原因是普通用户样本太少，错误反馈容易造成灾难性遗忘，而且训练会显著增加安装、硬件和解释成本。

向量模型也不进入默认检测路径。SQLite、倒排词典和结构化规则足以完成第一阶段学习。如果后续确实需要“相似案例召回”，再增加 `bge-small-zh-v1.5`：24M 参数、中文优先、MIT 许可证；不选择 0.6B 以上的 BGE-M3 或 Qwen3-Embedding。

官方资料：[bge-small-zh-v1.5 模型卡](https://huggingface.co/BAAI/bge-small-zh-v1.5)

## 8. 资源预算

以下均为工程预算，不是已经测得的最终数字：

| 组件 | 模型规模/文件预算 | 运行策略 |
| --- | --- | --- |
| Qwen3.5-4B Q4 | 约 2.7～3.4GB | 只处理歧义片段和局部图片 |
| PP-OCRv6 medium | 34.5M 参数；模型文件与运行库待打包实测 | 只对图片、扫描页和内嵌图片加载 |
| PP-DocLayoutV3 | 33.3M，约 132MB F32 | 复杂视觉页面按需加载 |
| SiameseUIE Chinese base | 官方仓库约 409.5MB | 若通过评估，批量文本扫描时加载 |
| Qwen3.5-9B Q4 | 约 5.5～6.5GB | 可选包，替换 4B，不同时加载 |

预计默认模型权重合计约 3.4～4.3GB；加上桌面应用、OCR/ONNX/LLM 运行库、字体和回退组件，完整离线安装预算为 **6～9GB**。最终发布预算需要以双平台安装包实测为准。

硬件分档建议：

| 档位 | 建议能力 |
| --- | --- |
| 8GB 内存 | 轻量模式：small OCR、较小语义模型或限制 LLM 使用、较小批次 |
| 16GB 内存 | 默认模式：Qwen3.5-4B Q4 + medium OCR，模型顺序加载 |
| 24GB 及以上 | 可选 Qwen3.5-9B 高准确度模式 |

16GB 是“适合普通用户”的合理推荐线，但现在不能承诺具体每页速度。峰值内存、首字延迟、每页耗时和能耗必须在代表性 Windows 与 Mac 设备上测量。

## 9. 许可证与供应链

| 组件 | 许可证 | 当前判断 |
| --- | --- | --- |
| Qwen3.5 | Apache 2.0 | 可商用，发布时保留许可证和声明 |
| PaddleOCR / PP-DocLayoutV3 | Apache 2.0 | 可商用，记录具体模型与代码版本 |
| SiameseUIE | Apache 2.0 | 可商用，仍需核对下载包内文件 |
| GLiNER2 | Apache 2.0 | 许可证可用，但中文能力不满足当前要求 |
| bge-small-zh-v1.5 | MIT | 可作为后续可选组件 |
| llama.cpp | MIT | 可作为本地 LLM 运行时 |

发布时不能从不明来源直接捆绑社区量化文件。推荐流程是：

1. 固定官方原始权重的版本或提交。
2. 在受控环境中转换和量化。
3. 对原始权重、转换工具和产物记录 SHA-256。
4. 在转换前后跑同一评估集，量化造成的召回率下降超过门槛则拒绝发布。
5. 离线包附带第三方许可证、模型卡和软件物料清单。

## 10. 开发前模型验证门

### 10.1 评估集

至少建立：

- 1,500～3,000 条中文为主的文本片段，覆盖个人、组织、财务、业务和自定义实体。
- 300 页视觉样本，覆盖原生 PDF、扫描 PDF、截图、拍照、旋转、低对比度、表格和 Office 内嵌图片。
- 正例和难负例同时存在，例如“王者荣耀”中的“王”、普通金额与敏感预算、公开公司名与保密客户名。
- 同一实体跨段落、跨文件、带空格、别名、简称、繁简体和 OCR 错字的情况。
- 所有样本使用合成或合法授权数据，不把真实客户隐私带入开发库。

### 10.2 指标

按实体类型分别统计，不只看总平均：

- 精确匹配 Precision、Recall、F1。
- 宽松边界召回率和字符级召回率。
- OCR 文字召回率、字符错误率和框位置误差。
- LLM 固定 JSON 成功率、原文 span 对齐率和重复运行一致性。
- 自动导出阈值下的漏检率和误处理率。
- 单页/千字耗时、峰值内存、模型切换耗时和安装体积。

建议发布门槛：

- 有校验规则的高风险号码召回率不低于 99.5%。
- 姓名、机构、地址的组合流水线召回率不低于 95%。
- 清晰印刷体 OCR 文字召回率不低于 98%，退化图像单独报告。
- 受约束输出的有效 JSON 比例不低于 99.9%。
- 16GB 基准设备峰值内存不超过 10GB。
- 任何声称可跳过复核直接导出的策略，必须单独通过残留验证测试。

这些数值是项目门槛，不是对模型当前能力的断言。未达到时优先调整规则、切块、候选合并和自动处理阈值，再决定是否升级模型。

### 10.3 需要运行的对比组

1. 规则和词典。
2. 规则 + Qwen3.5-4B。
3. 规则 + SiameseUIE + Qwen3.5-4B。
4. 规则 + PP-UIE-0.5B + Qwen3.5-4B。
